# Git setup and publishing

## Inspect and agree

1. Identify the project directory. Run `git rev-parse --show-toplevel` and compare it with the intended root. A starter folder can have no local repository or sit within a parent's checkout. If the root matches, inspect `git branch --show-current`, `git status --short --branch`, `git diff --cached`, and `git remote -v`. Preserve existing staged changes and redact any embedded credentials when reporting URLs. A blank branch can indicate a detached checkout.
2. Ask whether a GitHub repository exists, its URL, or whether the owner wants a new empty repository. Check that remote separately with existing sign-in, for example `git ls-remote --symref APPROVED_URL HEAD` and `git ls-remote APPROVED_URL`. A successful listing with no refs differs from a failed access check. Confirm the intended branch and history before linking an existing remote. Ask before initializing Git or changing a remote.
3. If the owner will create the remote, give a short first response with a suggested repository name, one-line description and visibility recommendation. Ask the owner to leave README, `.gitignore` and license unset for the empty remote. Wait for confirmation and the URL. Confirm the license choice separately before adding a license. Keep repository creation, visibility and checkpoint publication explicit. [Create a GitHub repository](https://docs.github.com/en/repositories/creating-and-managing-repositories/creating-a-new-repository)

## Opt into local-only workflow records

Agree on the exact paths before the first checkpoint. The owner may choose to keep role instructions, project plans and memory, agent settings, the session helper and runtime local while publishing source, README and product documentation. Keep runtime, real environment files, credentials, private prompts, session IDs, envelopes and private logs ignored and untracked in either mode. Use explicit paths for private files that lack a standard name. Apply local exclusions through the repository's `info/exclude` or agreed shared rules in `.gitignore`. Use `git rev-parse --git-path info/exclude` to locate the local exclusions. Confirm that any exception such as `.env.example` contains placeholders only.

Review the candidate tree with a temporary index (`GIT_INDEX_FILE`). In that temporary environment, seed it with `git read-tree HEAD` for a repository with a commit or `git read-tree --empty` for an unborn branch. Add only approved paths, review `git diff --cached` and use `git ls-files` to inspect the full candidate tree. Use `git check-ignore --no-index -v -- PATH` on expected local paths and inspect the staged content for private data. Restore the prior index environment and remove the temporary index after review. The [worktree guide](WORKTREES.md) shows how to isolate the index in either shell.

For previously tracked paths, review `git --literal-pathspecs rm --cached --dry-run -- PATH`, with `-r` only for an explicitly approved directory. Use the same command without `--dry-run` in the temporary index to review staged removals. Apply the reviewed removals to real staging only with checkpoint approval. Verify the working files still exist and the candidate tree excludes them. A cleanup commit removes files from the current tree. Earlier commits retain them. [Git index-only removal](https://git-scm.com/docs/git-rm)

Keep an owner-controlled backup of local workflow records. For a fresh clone, restore the approved local setup and exclusions before staging. For a worktree, use the [local briefing procedure](WORKTREES.md#local-only-workflow-records). If the owner requests a local credential file, check the ignore and tracking status before creating it and verify owner-only OS permissions. Keep secrets out of arguments, logs and handoff text.

## Publish an approved checkpoint

Skip empty checkpoints when the working tree and index are clean. Otherwise propose a Conventional Commit with exact paths and the target branch. The owner can publish personally or explicitly authorize the agent to stage, commit and push that checkpoint through the local terminal. Reuse the configured Git identity and existing sign-in. Inspect staged paths and content before committing, and verify the updated remote branch points to the expected commit after pushing. Preserve other staged changes and existing history. Keep tags and releases with the owner. Omit AI signatures, promotion and co-author trailers.
